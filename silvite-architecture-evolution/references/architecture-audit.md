# Architecture Audit

## 建立现状图

从用户行为沿真实调用链绘制，不从期望分层倒推：

```text
UI
→ 应用编排
→ 状态机
→ 协议与序列化
→ 传输
→ 平台能力
→ 外部设备或服务
```

对每一层记录输入/输出、依赖方向、状态所有者、生命周期、并发任务、持久化、权限、外部副作用、错误传播、超时/取消、重试、fallback、日志与关联 ID。

同时标记：

- Windows、Android 或其他平台的重复行为与平台特有实现；
- edition 能力差异和发布差异；
- 仓库之间共享的契约、不同的目录与禁止同步内容；
- 随包工具与系统工具、环境变量、缓存和子进程边界；
- 内容数据、脚本、插件和可执行代码的信任边界；
- Dead Code、兼容桥及仍在使用它们的消费者。

事实来自代码、日志、构建配置、测试和可复现实验。推断附反证方式；未知项写明会阻止哪个迁移决策。

## 状态与能力所有权

为每个状态定义语义、唯一所有者、触发事件、允许迁移、权限、副作用、超时和恢复路径。特别分离：

```text
Discovered ≠ Connecting ≠ Connected ≠ Authenticated ≠ Ready
```

- Discovery 只产生候选和可观察事实，不隐式获得连接权限。
- Connecting 必须由明确事件或策略触发，并满足权限、用户意图和可信身份条件。
- 自动重连必须绑定已验证身份、有限重试、取消、退避和 fallback；网络地址本身不是可信身份。
- UI 展示状态不得反向成为业务状态源。

若多个布尔量组合才能解释状态，或恢复依赖历史事件，建立显式状态机而不是继续增加标志位。

## 生命周期审计

对传输、音频、设备会话、后台任务和平台资源回答：

1. 谁创建、启动、暂停、取消和释放？
2. 所有权能否转移，转移事件是什么？
3. 并发启动、重复释放、断线重连和应用退出如何处理？
4. 平台权限被拒绝或资源被系统回收时状态如何变化？
5. 哪些日志证明资源最终释放且没有孤儿任务？

不允许 UI 生命周期偶然拥有底层资源，也不允许 catch-all 吞错后继续报告 Ready。

## 找到迁移 seam

选择能同时满足以下条件的边界：

- 输入输出可描述并可捕获；
- 当前与目标实现可在短期内同时挂接；
- 行为不变量能在边界测试；
- 切换失败可以回到 Known-Good；
- 不需要一次修改所有调用方。

优先在契约、适配器、状态事件或序列化边界建立 seam。若 seam 需要大量类型判断、布尔开关或双向依赖，重新划分边界。

## 审计输出

完成审计时交付：现状组件图、状态/生命周期表、依赖与副作用清单、差异矩阵、Known-Good 数据路径、最早异常边界、候选 seam、未知项和第一项可逆实验。
