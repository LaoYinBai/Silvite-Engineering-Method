# Compatibility and Versioning

## 兼容合同

按消费者而不是按文件定义兼容性：旧客户端、新客户端、旧服务、新服务、旧协议、存量数据、安装器、更新器、插件和外部设备分别能接受什么。

记录兼容方向、版本窗口、能力缺失行为、降级路径、错误语义、数据读写规则和退役时点。若新旧双方可能独立升级，至少验证旧→新、新→旧以及混合版本重连。

## 能力协商

用显式能力表达可选功能，不用版本号猜功能，也不用连接成功推断业务 Ready：

```text
身份与协议版本
→ 能力探测
→ 兼容性判定
→ 生命周期协商
→ 启用能力或明确降级
```

能力声明必须有稳定语义、未知值处理、超时、错误、fallback 和观测信号。旧端忽略未知能力时不得改变核心行为。

## 扩展点准入测试

只有全部满足时才建立扩展点：

1. 未来能力有明确用户或系统场景；
2. 已知变化轴和不会变化的边界语义；
3. 当前至少一个真实消费者，或预留成本极低且不改变当前路径；
4. 协议版本和能力协商规则明确；
5. 能力缺失或失败时核心可降级；
6. 有可观察测试、回滚和删除条件。

禁止万能接口、未使用插件点、大量布尔开关、空实现占位，以及为可能永远不出现的需求重构整条链路。

## 版本身份模型

把以下字段视为一个发布身份，而不是独立字符串：

| 字段 | 作用 |
|---|---|
| ProductVersion | 用户/协议可理解的产品版本顺序 |
| Build | 同一或跨版本的构建身份，必须遵循项目定义的全局单调规则 |
| Commit | 产物对应的不可变源码身份 |
| Channel | stable/beta/rc 或项目定义的分发通道 |
| Edition/Platform | 能力与包身份边界 |

## 更新器比较门禁

发布前读取并测试已安装客户端真正执行的比较谓词。明确它是 SemVer 优先、Build 优先、元组比较、两个字段都必须增大，还是按 Channel 分支。

必须包含以下反例：当前为 `2.4.0 Build 81`，候选为 `2.4.0 Build 82`；若更新器要求 ProductVersion 与 Build 都增大，候选不会被识别为更新。此时提高 Build 或成功上传 manifest 都不能证明可升级。

为 stable、beta、rc 和跨通道路径建立字面量测试数据，覆盖相等、回退、跨版本 Build、预发布转正式以及异常 manifest。候选身份必须同时满足比较谓词、通道策略、签名与回滚要求。
