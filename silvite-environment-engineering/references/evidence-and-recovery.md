# Evidence and Recovery Gates

## 测试器也需要验收

接受测试报告前保存并核对：工件身份、命令、开始与结束标记、完整 stdout/stderr、退出码和环境身份。验收结论应能在不依赖原 Agent 叙述的情况下重建。

重点检查：

- 循环是否枚举当前全部目标；
- `set -e`、算术表达式、管道、`head`/`tail` 或超时是否改变退出语义；
- 交互式脚本在无人输入时是否只是取消；
- assertion 是否检查输出文件、状态或行为，而非只检查管道末端；
- 报告的统计单位是脚本、断言还是测试套件；
- 历史报告是否比当前工件更旧。

报告无法由原始输出重建时，将其作为线索，不作为完成证据。

## 数量与引用完整性

先定义集合，再计算数量：

```text
全集 = 当前验收范围内所有实际成员
增量集 = 本次相对基线新增的成员
阶段集 = 特定阶段交付的成员
已执行集 = 本次运行真正到达的测试入口
```

“新增 N 个”只描述增量集，不能推导全集大小。文档目录、自然语言清单和文件系统数量不一致时，分别报告，并以验收合同指定的真实 artifact 集合重建。

对报告中的每个引用执行 referential-integrity 检查：文件存在且类型正确；大小、版本、hash 与清单一致；脚本入口可定位到同一版本；测试入口确实枚举该文件。缺少任一环节时，不得把引用项计为已验收。

## Artifact-over-report Failure Mode

以下任一现象表示验收链失真：

- 报告统计与 filesystem 或 runner 枚举不一致；
- 清单引用不存在、改名或不同版本的文件；
- 报告声称完整执行，但原始日志提前结束或退出码非零；
- hash 对应源文件，运行入口却指向另一副本；
- cold start/stop 只有步骤描述，没有带前态与后态的真实运行记录。

处理方式：冻结报告为待审计输入；保存冲突；从 artifact 重新计数与重放；只声明机器证据支持的最高状态。修复报告不能抹掉原冲突，它是后续回归场景的来源。

## Dry-run 合同

一个可信 dry-run 应：

- 使用与 apply 相同的参数解析和目标解析；
- 展示精确目标、计划动作与排除项；
- 不创建目标文件、不安装软件、不改配置；
- 对未知参数失败，而不是静默当作路径；
- 返回能区分“预览成功”“用户取消”“前置条件失败”的退出码。

需要确认的 apply 操作不是 dry-run。

## 备份门禁

1. 冻结源集合、目标归档与敏感数据政策。
2. 防止输出目录被递归包含进输入集合。
3. 将排除规则实际传给归档/复制实现。
4. 列举归档成员，抽查敏感模式和异常链接。
5. 在归档关闭后生成校验和，并记录可移植的校验引用。
6. 将成功条件建立在归档存在、非空、可读取且成员符合合同之上。

manifest 中写着“已排除”不能替代实际成员审计。

## 恢复门禁

1. 校验和不匹配时停止。
2. 解包前拒绝绝对路径、父目录穿越及越界链接。
3. 先恢复到隔离目录并生成覆盖计划。
4. 保护当前目标并给备份赋予可追踪身份。
5. apply 后验证权限、所有者、语法和目标功能。
6. 失败时从刚创建的回退点恢复，并记录剩余差异。

恢复验证应使用无敏感数据的受控样本；不要为了测试破坏唯一真实环境。

## 诊断包与隐私

逐个数据源建表：采集目的、潜在敏感字段、过滤方式和人工复核。特别审查进程完整命令行、HOME 下路径、远程地址、DNS、环境变量、工具配置与错误输出。

只有最终产物经过内容审查后，才能说明已覆盖哪些脱敏项。使用环境变量白名单不代表其他命令输出自动安全。
