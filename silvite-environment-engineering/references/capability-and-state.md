# Capability and State

## 状态阶梯

环境能力按层验证，不相互蕴含：

| 状态 | 示例证据 | 不能证明 |
|---|---|---|
| 可获得 | 仓库元数据中存在包 | 已安装 |
| 已安装 | 包管理器记录 | 命令名、PATH、加载状态 |
| 文件存在 | 精确路径与类型 | 可执行或适用于当前架构 |
| 可解析 | `command -v`/等价机制返回路径 | 功能正确 |
| 已加载 | 新会话中配置生效 | 端到端行为正确 |
| 功能可用 | 代表性真实操作成功 | 重启后持久 |
| 生命周期可用 | fresh/cold 场景成功 | 可恢复 |

## 包名与命令名

安装列表使用包标识，运行时检查使用二进制或功能入口。一个包可能提供多个命令，命令名也可能与包名不同。

安装前后分别验证：

```text
包管理器：目标包的安装状态与版本
解析器：目标命令解析到的绝对路径
运行时：版本/帮助或无副作用探针
能力：与用户需求等价的最小操作
```

不要用 `command -v <package-name>` 判断包是否安装，也不要因一个常见命令名不存在就直接建议重装。

## Shell 与配置加载

先区分 login/non-login、interactive/non-interactive，以及应用是否自行覆盖 Shell 参数。配置修改后：

1. 静态检查语法；
2. 创建与用户实际入口相同类型的新会话；
3. 验证配置确实被读取；
4. 执行目标功能；
5. 若声明持久，再验证所需生命周期。

`source` 适合即时试验，不是持久性证明。旧 Shell 中已存在的 alias、函数或环境变量也不能证明磁盘配置正确。

## 路径与可执行权限

检查实际调用方式：`bash script.sh` 需要可读文件与可用解释器，直接执行 `./script.sh` 还需要执行位和有效 shebang。不要把统一 `+x` 当作与调用方式无关的质量指标。
